## Commands

- Install dependencies: `pip install -r requirements.txt`
- Run the app: `streamlit run app.py`
- Retrieval eval (no LLM, no API calls; uses a throwaway store, not `./vector_store`): `python tests/eval_retrieval.py`. Runs two variants over the `docs/medical/` test set: cosine only (top-3 11/14, top-5 12/14, mean worst-evidence rank 1.92, ~26 ms/search) and with the reranker (top-3 12/14, top-5 13/14, mean rank 1.54, ~700 ms/search warm). Also prints precision@k / recall@k (macro-averaged over the 14 answerable questions): cosine only P@3 0.38, R@3 0.87, P@5 0.27, R@5 0.94; with the reranker P@3 0.45, R@3 0.94, P@5 0.30, R@5 0.96. A chunk counts as relevant if it contains any of the question's evidence strings, recall is the share of evidence strings found in the top k, and precision divides by the chunks actually returned (the threshold can return fewer than k); precision is understated because on-topic chunks without the exact evidence string count as irrelevant, so compare variants rather than reading it as an absolute. The mean rank only covers questions where all evidence was found. Uses the raw question as the query, so it understates the agent (which rewrites queries).
- Generation eval (calls Groq; uses a throwaway store; on demand, it spends free-tier rate limit): `python tests/eval_generation.py` (`--only 12,14`, `--repeat N`, `--show`, `--real-store`). Runs the real agent + `verify_answer` on the 16 `docs/medical/QUESTIONS.md` questions and checks the answer text against key facts (`REQUIRED`/`FORBIDDEN` in the script); API failures count as ERROR, not FAIL. Baseline (one full run with `--repeat 3`, 48 runs, 0 errors): answerable 13/14 questions (40/42 runs, 95.2%), refusals 2/2 (6/6 runs), 0 `verify_answer` warnings, ~1.1 searches and ~9.4 s per question. Everything passes 3/3 runs except Q3, which passed 1/3: it omits "supporting documents" and gives separate Summit and Medicare lists from a single search (the retrieval eval finds that evidence at rank 1, so it is stored; the model just doesn't pick it up). Q12 passed 3/3 and a manual read confirmed Summit's 60 days and Medicare's MSN deadline are attributed separately. Two key facts were loosened after the first run because the model's wording was correct but didn't match (Q12 accepts the filename instead of "Summit", Q14 accepts "12-month"). Three samples per question is still small. It checks that facts are present, not that a cited chunk supports them, and cannot tell which organisation a fact belongs to (Q12 needs a manual read).

- Load the bundled docs into the persistent store (no UI upload needed): `python ingest_docs.py [folder]` (default `docs/medical`). Safe to re-run (unchanged files skipped, changed ones replaced); ignores unsupported extensions. Reuses `core.interaction.ingest_and_store`.

## Architecture so far

- `app.py` — Streamlit UI only (file uploader + question input + response display). Contains no document or RAG logic; it just calls `handle_query()`.
- `core/interaction.py` — `handle_query(files, question)` is the single seam between the UI and the pipeline. Files are optional: if given, they're ingested/chunked/stored (adding to the knowledge base); the question then always retrieves against the *full* persisted vector store, not just files from the current submission — so a user can ask follow-up questions without re-uploading. It first validates the question and upload count/sizes (`core/safety.py`; rejections come back as messages), skips already-stored documents (identical content), replaces a document whose filename is already stored but whose content changed (the new chunks are stored first, then the old version's chunks are deleted, so a failure or an empty new version never loses the old one; files are matched by name only, so two different files with the same name are treated as versions of one document), then after ingestion does an empty-store check and calls `run_agent(question)`; the answer goes through `verify_answer()` and any warnings are returned for `app.py` to show with `st.warning`. It returns a `QueryResult` (text = upload summary + answer + numbered Sources list of the chunks the agent retrieved; steps = the agent's tool calls, which `app.py` shows in a collapsible "Agent steps" expander).
- `core/ingestion.py` — Converts uploaded files into plain-text `Document` objects. Dispatches by file extension to a parser: `pypdf` for PDF (text pages are cleaned: trailing/double spaces removed, `•` -> `-`, space before punctuation removed, hard-wrapped lines reflowed into paragraphs, and running headers/page numbers dropped — a short line in the top/bottom 2 lines of a page that repeats on 2+ pages is kept once, only for PDFs of 4+ pages; OCR'd pages are never cleaned. Known gaps: near-full-width list/table rows can merge into one line, and reflow doesn't join paragraphs across page breaks), `python-docx` for DOCX, `beautifulsoup4` (+ `lxml`) for HTML/HTM, built-in read for TXT, `pandas` for CSV/Excel. CSV/Excel rows and DOCX table rows are rendered as `col: val, col: val, ...` (header repeated per row) rather than a raw table dump, so each row stays self-describing once it's flattened to text (a DOCX table's first row is assumed to be its header). DOCX headings become `#` lines, in document order with tables. HTML: drops `script/style/svg/nav/footer/header/aside/form/button/input`, then reads headings/paragraphs/list items from `<main>` (falls back to `<body>` if the page has no `<main>`); links keep their text only. Scanned content is OCR'd: any PDF page with under 10 characters of extracted text is rendered with `pypdfium2` and OCR'd (per page, so mixed PDFs work; a PDF needing OCR on more than `MAX_OCR_PAGES` = 20 pages is rejected), and images of at least 100x100 px inside a DOCX are OCR'd and appended after the body text (first 20 only; unsupported image formats such as EMF/WMF are skipped). Parse errors are caught per-file and surfaced as `Document.metadata["error"]` rather than raising, so one bad upload doesn't fail the whole batch. Not handled: legacy `.doc`, DOCX headers/footers/text boxes/footnotes, nested DOCX tables, handwriting (a handwritten-style signature was misread in testing).
- `core/ocr.py` — `image_to_text(image)` runs RapidOCR (ONNX, local, no API key; engine created lazily once per process) and regroups the returned text boxes into lines by vertical position, so a form's "Label:   value" stays on one line. The grouping tolerance was tuned on a single-column form; multi-column scans may interleave. About 4 s per page on CPU. The ~31 MB of ONNX models are not in the pip package: RapidOCR downloads them (from modelscope.cn) into its own `site-packages/rapidocr/models/` on the first OCR call, so a deployment needs internet on first use or must pre-download them at build time.
- `core/chunking.py` — Splits a `Document`'s text into `Chunk` objects (~500 chars, ~50 char overlap by default). Character-based, not token-based, since no embedding model/tokenizer is chosen yet. Splits recursively on paragraph breaks first, then sentences, then words, then raw characters as a last resort, so chunks break at natural boundaries where possible. No page tracking, no semantic/topic-aware splitting. Tried and rejected: heading-aware splitting with a `Section: ...` prefix on each chunk (DOCX/HTML) — on the 14-question retrieval eval top-3 stayed 11/14 and top-5 12/14 and the mean evidence rank got slightly worse (Q3/Q9/Q10 improved, Q2/Q13 worsened), so it was not kept. In that eval the evidence was always whole inside one chunk, so chunk boundaries aren't the bottleneck; the misses (Q12, Q14) were ranking (evidence at rank 6) plus near-duplicate chunks taking top-k slots; the reranker fixed Q14 (now top-5) but not Q12.
- `core/vectorstore.py` — Embeds chunks with `sentence-transformers` (`all-MiniLM-L6-v2`, local, no API key) and stores them in Chroma (`PersistentClient`, embedded — no server), persisted to `./vector_store/`, using cosine similarity (`hnsw:space: "cosine"`) to match how the embedding model is tuned. `add_chunks()` embeds + stores. Dedup: each stored chunk's metadata carries a SHA-256 `content_hash` of its document's extracted text; `find_by_hash()` lets ingestion skip re-uploads of identical content; `ids_for_source()` / `delete_ids()` let ingestion swap out an older version of a same-named document (documents stored before Phase 8 have no hash, so they aren't detected). Model guard: the collection's metadata records the embedding model (`embedding_model`); on first open `get_collection()` raises `EmbeddingModelMismatch` if it differs from `EMBEDDING_MODEL_NAME` (`handle_query` turns that into a message telling the user to delete `vector_store/` and re-upload — there is no automatic re-index). A store with no recorded model (older, or new/empty) is stamped; if it has data, it's only stamped when its vector dimension matches the model (an unverified assumption, logged as a warning) — a different model with the same dimension can't be detected that way. Chroma ignores new metadata on an existing collection and `modify()` replaces metadata wholesale (cosine lives in the collection config, so it survives). The model and Chroma client are lazily initialized once per process (`_get_model`/`get_collection()`) rather than on import. `get_collection()` is public — `core/retrieval.py` queries it directly.
- `core/retrieval.py` — `retrieve(question, top_k=5)` embeds the question with the same model used for stored chunks, queries the collection, and returns `RetrievedChunk`s (text, source, chunk_index, cosine-similarity score). Returns `[]` if the store is empty. `list_sources()` returns `{source: chunk_count}` for the agent's `list_documents` tool. Results scoring below `MIN_SCORE = 0.25` are dropped (so it can return fewer than `top_k`, or `[]`). 0.25 was chosen from a small calibration with all-MiniLM-L6-v2 — unrelated questions scored <=0.16, relevant ones 0.37-0.76 — and is a heuristic to re-tune per corpus. Reranking: `retrieve()` fetches `RERANK_CANDIDATES = 20` by cosine, drops those below `MIN_SCORE`, then a cross-encoder (`cross-encoder/ms-marco-MiniLM-L-6-v2`, local, lazy-loaded, ~90 MB downloaded on first use) re-scores (question, chunk) pairs and the best `top_k` are returned. `RetrievedChunk.score` stays the cosine value (the threshold and the Sources list use it); `rerank_score` holds the cross-encoder logit. `USE_RERANKER = True` in `core/retrieval.py` switches it off; `retrieve(..., rerank=True/False)` overrides per call. If the reranker fails it logs and falls back to cosine order. Costs ~700 ms per search (vs ~26 ms), and the agent can search up to 5 times per question. The 0.25 cosine cutoff still decides refusals: off-topic questions can still pass it (e.g. the dental-care eval question, best 0.52), so refusing then relies on the LLM. Remaining eval miss: Q12 (second evidence string never reaches the top 5); a larger candidate pool is untested.

- `core/safety.py` — Deterministic guardrails, no LLM calls, no dependencies. Limits: question 1000 chars (control chars stripped), 10 MB per file, 10 files per submission, 2M chars extracted text per document (enforced in `ingest`), 20 OCR pages/images per document (`MAX_OCR_PAGES`, enforced in `ingestion.py`). `verify_answer()` first rewrites the model's off-format citations (full-width `【2】`, or with a line-range suffix `【1†L1-L3】`, which `openai/gpt-oss-120b` emits despite the prompt) to `[n]`, then strips `[n]` citations that don't match a retrieved chunk and returns warnings (invented citations removed; answer cites nothing; answer wasn't based on a search). It checks that a citation exists, not that it supports the claim. A greeting answered without searching also gets the 'not based on a search' caution (known false positive). `REFUSAL_SENTENCE` is the exact refusal text; `is_refusal()` is used to hide the Sources list on refusals.
- `core/logger.py` — File logging to `app.log` in the project root (errors, tool failures, fallbacks, rejected inputs, skipped duplicates). Never logs document or question text.
- `core/generation.py` — `generate_answer(question, retrieved)` calls Groq (`groq` SDK, model constant `MODEL = "openai/gpt-oss-120b"` (Groq retired its Llama chat models; list what your key can use with `get_client().models.list()`; a 404 model_not_found now produces a message saying so), temperature 0.1) with a system prompt restricting answers to the numbered context blocks, refusing with "I don't know based on the provided documents." otherwise, and citing blocks inline like `[1]`. Requires `GROQ_API_KEY`, read from the environment or from a `.env` file in the project root (loaded with `python-dotenv` in this module; real env vars take precedence; `.env.example` shows the format, `.gitignore` excludes `.env`). Missing key / auth / rate-limit / connection / API errors are returned as readable strings rather than raised. Non-streaming, no conversation memory, citations are prompt-enforced not verified. The client is lazily initialized once per process, with a 30 s timeout and 3 SDK retries. Context is wrapped in `<document source=… chunk=…>` tags with an `UNTRUSTED_CONTEXT_RULE` in the system prompt (prompt-injection hardening; a `</document` inside document text is escaped). With no retrieved chunks it returns the refusal sentence without calling the model. `get_client()`, `api_error_message()` and `MISSING_KEY_MESSAGE` are shared with the agent; `generate_answer` is the single-shot (non-agent) path, used now only as the agent's fallback.
- `core/agent.py` — `run_agent(question)` is a hand-rolled tool-calling loop on Groq's native tool calling (no framework). Tools: `search_documents(query)` (wraps `retrieve()`, top 5) and `list_documents()`. The model chooses tools, sees results, and loops until it returns plain text; capped at `MAX_STEPS = 5` tool rounds, after which a final call with `tool_choice="none"` forces an answer. Search results are numbered blocks with run-wide stable citation numbers (a repeated chunk keeps its number). Tool failures (bad JSON args, unknown tool, exceptions) go back to the model as text rather than raising. A malformed tool call from the model (Groq 400) is retried once, then falls back to retrieve + `generate_answer`. Returns `AgentResult` (answer, steps, chunks, `failed` — True when `answer` is an error message). A search with nothing above the relevance threshold tells the model so, prompting a rephrase or a refusal. The system prompt allows answering without a search only for pure greetings/thanks; every other question (including medical/legal/financial advice) must be searched first, and if the documents don't cover it the model must give the exact refusal sentence, not decline in its own words. It also tells the model that when different documents give different answers to the same question it must report each separately and name its source rather than merge them. No conversation memory; no score threshold; citations prompt-enforced, not verified. Multi-call questions use more of the Groq free-tier rate limit.

## Planned phases

1. **User interaction layer** – Simple interface or API to upload documents and ask natural language questions.
2. **Document ingestion** – Upload and process enterprise documents in multiple formats (PDF, TXT, CSV, Excel).
3. **Chunking for semantic search** – Convert processed document content into chunks suitable for embedding and retrieval.
4. **Vector-based knowledge store** – Generate embeddings and store them in a vector database for semantic similarity search.
5. **Document retrieval** – Retrieve the most relevant document content for a query via similarity search.
6. **RAG pipeline** – Combine retrieved context with an LLM to generate grounded responses.
7. **Agent-based reasoning** – AI agent(s) that plan, retrieve, reason, and generate responses using available tools.
8. **Reliability and safety controls** – Error handling, input validation, and guardrails against hallucinations and unsafe outputs.
9. **Deployment and documentation** – Document architecture, workflow, and limitations (`README.md`) and publish the code to GitHub. Actual deployment was dropped from scope.

Update this file as the stack, structure, and tooling are decided per phase.
